== Where the daily work is documented

The daily work, installing, copying repositories, updating them, signing in, trusting a repository, installing a kit,
recovering when something fails, is documented by `ws-host help`, and nowhere else.

----
ws-host help            # the topics
ws-host help repos      # one topic
----

In VS Code, use Learn. It lists the same topics and shows each as a page whose steps are buttons, so you learn by doing.
Part IV reproduces every topic from the same code (<<reference-help>>), which is the only reason that copy can be trusted:
it is generated, and `ws-host fresh` fails if it is out of date.

== Keeping `ws-host` current

`ws-host` improves often. One command brings the newest version, and it only ever moves forward, so your own changes are safe:

----
ws-host update
----

Every new terminal window looks for news in the background, at most every six hours and without making you wait. When a newer version is
ready, the window says so in one line, and `ws-host update --check` shows what is new. `ws-host doctor` reports it too. `ws-host workspace ensure`
brings `ws-host` up to date along with your repositories, so running it is enough. The check lives in the marked lines of your `~/.bashrc` (or
fish's `config.fish`) that `ws-host shell add` writes, so deleting the lines that mention `update` turns the reminder off.

The cloud command lines (`aws`, `az`, `wrangler`, `railway` and the rest) and the modern terminal tools (`eza`, `bat`, `delta` and the rest) always float with their newest
release, and they change often. `ws-host update` leaves them alone so that it stays quick. When you want them current, run:

----
ws-host update --tools
----

`ws-host kit check` first tells you which are behind without changing anything, and `ws-host kit sync` is the same update for one kit's tools.

== Small databases: SQLite, DuckDB, Turso and MotherDuck

`base` installs `sqlite3` (with `sqldiff` and `sqlite3_analyzer`) and `duckdb`, always the newest release. On a machine that is not x86-64, sqlite.org has no build of its tools, so the
`sqlite3` of your distribution is the one you get, and setup says so. The `embedded-sql` kit, installed for you by default, adds what goes around them:

[cols="1,3"]
|===
|`turso` |the Turso command line, for hosted libSQL databases
|`usql` |one SQL client for SQLite, DuckDB, libSQL, Postgres and more
|`litestream` |continuous backup and restore of SQLite files
|`sqruff` |a SQL formatter and linter
|`dbmate` |database migrations
|`sqlite-utils`, `datasette` |load CSV and JSON into SQLite, and explore a file in your browser
|`harlequin` |a SQL editor in the terminal for SQLite and DuckDB
|`visidata` |explore any table-shaped file
|===

MotherDuck needs no program of its own: it is DuckDB. Put your token in `MOTHERDUCK_TOKEN` and run `duckdb`, then `ATTACH 'md:';`. ClickHouse is not part of the kit on purpose.

== How the terminal looks

At a terminal, `ws-host` shows sections with a heading, rows with a mark you read at a glance (✅ fine, ⚠️ look at this, ❌ failed, ⏭️ skipped,
⬜ not yet), and the next step in cyan on a line of its own, ready to copy. The first line is always one plain sentence. In a pipe, a file or
with `NO_COLOR` set you get plain text without marks, and `--json` and `--html` are never decorated. `WS_HOST_COLOR=always` or `never` decides
for you.

The one thing I put outside `help` is the first line you paste on a new machine, because `ws-host` is not there yet:

----
curl -fsSL https://raw.githubusercontent.com/intellectual-frontiers/workspaces-host/main/install.sh | sh
ws-host workspace ensure
----

The first checks for `git`, `curl` and `xz`, prepares ws-host's own Python and `uv`, copies `ws-host` beside your other repositories
and links it into `~/.local/bin`. The second does everything else, and you can run it as often as you like.
