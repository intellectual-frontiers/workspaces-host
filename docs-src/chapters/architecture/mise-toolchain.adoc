== mise and the provider toolchain

mise is the tool installer underneath `ws-host`. It does two jobs, and keeping them apart is the key to understanding the rest: it installs `ws-host`'s own Python and `uv` (see <<bootstrap>>), and it installs the programs every provider says it needs. `ws-host` never asks a person to use mise, and it never reads a person's own mise settings.

=== Three places a version is pinned

.Three places a version is pinned
image::figures/fig-3.1.png[Three boxes (bootstrap.env, toolchain.d, kit modules) feeding one box: a wrong fingerprint installs nothing,width=95%]

[cols="2,3,3"]
|===
|Pin |Holds |Checked by

|`ws_host/bootstrap.env`
|mise, Python and uv versions, and mise's SHA-256 for each architecture
|The launcher, before unpacking mise; `mise.lock` for Python and uv

|`.workspaces-host/toolchain.d/*.toml`
|The tools a provider needs: Node, Python, uv for this repository
|mise, from `mise.lock`, with `--locked`

|`ws_host/kits/*.py`
|A kit's downloads: Rust, `glab`, DuckDB, oh-my-posh, Chrome for Testing
|`install/fetch.py`, before unpacking
|===

The three are separate on purpose. Bootstrap must work with nothing installed, so it cannot use a provider file. Kits install tools a person asks for by name, in code a test can run. Provider tools belong to a repository, so they are declared beside it.

=== A provider declares; ws-host translates

A provider is a repository with a `.workspaces-host/` folder. This repository's is the model:

----
.workspaces-host/
  provider.toml          name, summary, launcher = "./ws-host", protocol = 1
  toolchain.d/
    node.toml            one file per tool; the file name is the tool name
    python.toml
    uv.toml
  mise/.config/mise/     generated: conf.d/*.toml and mise.lock
----

Each entry in `toolchain.d` is validated by `ws_host/lib/provider.py`:

* the version is exact: no range and no floating tag such as `latest`;
* the kind is `archive`, `npm` or `tool`;
* an archive names, for each of `linux-x64` and `linux-arm64`, an https URL and a 64-character SHA-256;
* `needs` forms a graph with no cycle;
* if two providers declare the same name and version differently, that is a conflict and is reported.

.How a provider names its tools
image::figures/fig-3.2.png[Four steps from a toolchain.d file to toolchain ensure with a locked install,width=95%]

`ws-host toolchain generate` turns the entries into mise configuration under `.workspaces-host/mise/.config/mise/conf.d/`. An archive becomes an `http:` entry carrying `checksum = "sha256:..."`; settings turn on `lockfile = true`. Each generated file begins with a "Generated by" header. The lock is `mise lock --platform linux-x64,linux-arm64`, so one commit covers both architectures.

`ws-host toolchain ensure` refuses to run on files that are `stale` (the declarations changed and nobody regenerated) or that have no lock. It then runs `mise install --locked` for the closure of what was asked for. `toolchain remove --unused` prunes store versions no enabled provider's lock names.

=== How mise is run

`ws_host/lib/mise.py` runs `mise -C <provider folder>` with:

* every inherited `MISE_*` variable removed;
* `MISE_CEILING_PATHS` set to the folder's parent, so mise never reads configuration above the provider;
* safe mode on, and its data, cache, state and config under `ws-host`'s own directories.

A provider's program runs through `ws-host provider run NAME -- argv`, which builds its environment from the same locked files. That is how other repositories' orchestrators, such as a private repository's, get the exact tools they were tested with.

=== What mise does not do here

* It does not install kits. Kits use `ws-host`'s own two installers (see <<kits-installers>>).
* It does not manage your dotfiles. chezmoi writes those files (see <<chezmoi-managed>>).

The design notes behind these choices are in `spikes/mise/NOTES.md`. Three hazards were found there (content identity, environment scrubbing and the shims folder on the path); the decision was to keep mise's own name-and-version identity with a drift check, to let providers scrub their own children, and to activate mise the standard way. The lock format is tied to the mise version, which is why the mise version is pinned.

=== Prompts for maintenance

Bump a provider tool::
_Update Node in `.workspaces-host/toolchain.d/node.toml` to X. Use the real release URL and SHA-256 for both platforms, run `ws-host toolchain generate`, include the regenerated `conf.d` files and `mise.lock` in the change, then run `ws-host check providers`, `ws-host test` and `ws-host fresh`._

Add a tool a provider needs::
_Add `jq` as a provider tool. Create `toolchain.d/jq.toml` following `node.toml`, with exact version, https URL and SHA-256 for linux-x64 and linux-arm64. Regenerate and lock. Do not add a version range._

Diagnose a stale error::
_`toolchain ensure` says the files are stale. Find out which declaration changed, regenerate, and explain why the check caught it._

Files these touch: `.workspaces-host/toolchain.d/*.toml`, `.workspaces-host/mise/.config/mise/` (generated, commit all of it), `ws_host/lib/provider.py`, `ws_host/lib/toolchain.py`, `ws_host/lib/mise.py`, `tests/test_provider.py`.

CAUTION: Never ask an AI to hand-edit `mise.lock` or a generated `conf.d` file. Ask it to run `ws-host toolchain generate`. The generated files carry a header saying so, and `ws-host check providers` fails when they drift.
